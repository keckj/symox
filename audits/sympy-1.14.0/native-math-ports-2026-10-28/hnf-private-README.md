## Metadata and ordinary-HNF followup

The new modulo-D guard uses local, never-executed semantic templates for every skipped mathematical Python helper and relevant wrapper. It reads fresh function metadata via the accepted optional public native service, requires the actual function's cached builtins, and checks exact modules, namespace keys and containers before lookups/comparisons. Foreign keys, modules/readers, tuple subclasses, altered defaults/code, and cached foreign builtins decline without speculative callbacks. Unsupported metadata environments retain the complete algorithm. No private object layout or mutable function-data cache is introduced. Native entry is positively tested under a hook rejecting object.__getattr__ audit events.

Ordinary HNF receives a deliberately bounded followup: its `_gcdex` and `add_columns` captures must match two literal templates defined in that same guard, before their immutable code identities are stored. The templates are never executed. Four independently reproduced R12 cases (two helpers, returning/raising) now execute the real changed helper and preserve its result/error/callback, with no audit event or native admission. Other ordinary bootstrap captures remain the R12 implementation; this is not universal bootstrap authentication.

That revision and its 1680/9888 gates are explicitly rejected and preserved in a separate archive.
